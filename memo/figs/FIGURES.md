# Memo figures

Generated by `make_figs.py` (run with
`/work2/10240/bmason72/stampede3/casaenv/bin/casapy make_figs.py` from this
directory). Re-run any time the underlying CSVs change; the script is
deterministic and writes both the `.pdf` (for the memo) and a `.png` preview
of each figure.

All three figures reuse the shared curve engine end to end rather than
re-deriving envelopes:

* `sa_select/envelope.py` (`Envelope.curve`) does the (robust, taper) lattice
  interpolation (row/column segments + bilinear cell interiors).
* `curvegen/make_report.py`'s `build_curve()` and `build_heatmap()` are
  called directly (imported as `mr`), so the figures show exactly what the
  HTML report (`curvegen/revf-curves.html`) shows for the default
  `(rev=revF, sim_mode=track)` configuration -- same sample trimming
  (`eta <= ETA_CAP = 5`, matching `make_report.main()`), same beam-cap
  clipping (`max_res` from each subarray's `beam_cap_arcsec_30ghz`).
* Data source for all three: `sa_select/data/revf_curves.csv` (curve
  samples) and `sa_select/data/subarrays.csv` (beam caps, offered-set
  membership), resolved via `curvegen/make_report`'s own module-level
  defaults (`CURVES_CSV`, `SUBARRAYS_CSV`, `ACTIVE_ORDER` == `ORDER`).
* The offered set is `curvegen/make_report.ACTIVE_ORDER`, i.e. all 14
  subarrays currently collected for the default combo: `core-inner, core,
  spiral, mid, core+spiral, spiral+mid, main, long, mid+long,
  spiral+mid+long, main+long, spiral+core-outer, mid+spiral+core-outer,
  long+mid+spiral+core-outer`. (`core+mid` and `core-outer` alone are
  measured but not offered, and are correctly excluded because they are not
  in `ACTIVE_ORDER`.)

For legend readability with 14 curves, each figure splits them into two
panels sharing a y-axis (but not an x-axis): the **long-baseline family**
(left panel, 5 members: `long`, `mid+long`, `spiral+mid+long`, `main+long`,
`long+mid+spiral+core-outer`) and the **non-LONG family** (right panel, 9
members: `core`, `spiral`, `mid`, `core+spiral`, `spiral+mid`, `main`,
`core-inner`, `spiral+core-outer`, `mid+spiral+core-outer`). Membership is
decided on the `components` column of `subarrays.csv` -- i.e. on whether the
subarray actually contains LONG antennas -- not on a substring test against
the subarray's name; a name-based test would wrongly sweep the two
`core-outer` composites without LONG stations (`spiral+core-outer`,
`mid+spiral+core-outer`) into the long-baseline family, since `core-outer`
is just the outer 57 of the 114 Core antennas (memo 121's "outer50core").
Colors come from Paul Tol's 9-colour "muted" qualitative palette
(colorblind-safe and print-safe), needed because the non-LONG panel now
carries 9 curves -- more than the previous 7-colour Okabe-Ito set could
label without repeating a color within one panel. Colors are assigned by
position within each family list and still repeat across the two panels,
but each panel now carries its own legend directly beneath it (long-baseline
at 1 column, non-LONG at 2 columns, both running to 5 rows) rather than one
merged interleaved legend, because a merged legend would put two
same-colored entries from the two panels side by side.

The non-LONG family is ordered by natural-weight, untapered 30 GHz
resolution, finest native beam first (`order_by_natural_resolution`, called
from `main()` because the ordering needs the measured curves): `mid`,
`spiral+mid`, `mid+spiral+core-outer`, `main`, `spiral`, `spiral+core-outer`,
`core+spiral`, `core`, `core-inner`. Matplotlib fills a legend column-major,
so that legend reads finest-to-coarsest down the first column and on down
the second. The long-baseline family is still in `ACTIVE_ORDER` order.
Family names are drawn with `ax.set_title(..., loc="left")`, above each
frame rather than inside the axes.

## figs/taperability.pdf

Point-source (taperability) envelopes at 30 GHz: eta vs. resolution for all
14 offered subarrays, linear y-axis, log-x. Samples are still trimmed at the
report's own eta <= 5 display cutoff before the envelope is built, but the
axis itself is now truncated further, to eta in [1.0, `ETA_MAX_PTSRC` =
2.0] -- previously only the floor (1.0) was fixed and the ceiling floated to
the data; some curves now run off the top of the frame by design, since the
interesting structure is all near eta ~ 1-2. Built via
`mr.build_curve(samples_by[name], max_res=caps[name])`, i.e.
`Envelope(samples).curve(skirt_max=None, ...)` -- PSF shape (skirt) is
completely ignored, matching the point-source/"minimum eta" definition in
`sa_select/curves.py`.

Caveats for the caption:
* Curves are envelopes over the tabulated (robust, taper) lattice, not raw
  samples; gaps in the underlying sweep show up as a missing stretch of
  curve, not an interpolated guess (the engine does not extrapolate past a
  measured row's ends -- see `envelope.py`'s module docstring).
* The left panel (long-baseline family) reaches much finer resolutions
  (sub-milliarcsec for `long` alone) than the right panel's finest (`mid`,
  ~3 mas); the two panels intentionally do NOT share an x-axis so each
  family's own dynamic range is legible.
* Heterogeneous subarrays (`main`, `main+long`, `mid+long`,
  `spiral+mid+long`, `spiral+core-outer`, `mid+spiral+core-outer`,
  `long+mid+spiral+core-outer`) are clipped at their beam cap (the coarsest
  component's own native beam) -- see `subarrays.csv`'s
  `beam_cap_arcsec_30ghz` column; beams coarser than that are not offered
  from the composite array.

## figs/imaging.pdf

Imaging (sculptability) envelopes for the same 14 subarrays and layout,
built via `mr.build_curve(samples_by[name], skirt_max=mr.SKIRT_DEFAULT
(=0.10), max_res=caps[name])`. The y-axis is truncated to eta in
[1.0, `ETA_MAX_IMAGING` = 3.5] (a separate module constant from the
point-source figure's 3.0; both values were chosen by eye, not derived); as
in the taperability figure, some curves now run off the top of the frame by
design.

Legend layout: each panel carries its own subarray-name legend beneath it,
exactly as in the taperability figure. The strict/traded/relaxed line-style
key, by contrast, stays a single blended banner spanning the full figure
width below both panels -- it encodes line style only (no subarray
identity), so the two panels' repeating color palette does not make it
ambiguous. That banner is now positioned by `_banner_below`, which measures
the two just-drawn panel legends and hangs the banner immediately beneath
whichever of them reaches lowest, rather than at a hard-coded y-offset (the
two panels' legends are not the same height, since the families split
5/9 rather than 7/7).

**Important caveat the memo text should address explicitly**: the figure's
three visual states (solid = strict, dashed = "traded", dotted = "relaxed")
are **not** three states the current engine actually emits. As of the
8 Jul 2026 change documented in `sa_select/envelope.py`
(`Envelope.solve`'s `mode="threshold"`, the DEFAULT, and the mode used with
no override by `curves.CurveLibrary.solve` -- the real selector -- and by
`make_report.build_curve`), a curve point is only ever flagged `relaxed`
(skirt target not met within the beam-margin window; the best achievable
skirt is reported instead, uncensored by eta) or not (`strict`, meaning some
beam met skirt <= 0.10). `Choice.traded` is a residual field that is only
ever set `True` under `mode="legacy_trade"`, the **retired** one-for-one
eta-skirt trade -- which is what `ngvla_sa_selection.tex`'s "Curve engine:
query time" section currently describes in prose as the primary imaging
objective. That prose is stale relative to the shipped default policy.

To still deliver the three-way split the figure's own caption promises
("strict, traded, and relaxed segments visually distinguished"), this script
derives "traded" from the engine's own real output fields rather than
inventing a synthetic objective: a `relaxed` point is bucketed **traded**
if its reported `skirt <= 0.25` (the legacy trade's cap) and **relaxed**
(dotted) only if the best achievable skirt exceeds 0.25. No `mode` override
was requested from the engine -- this is a pure post-hoc, honest recoloring
of `curves.CurveLibrary`'s actual default answers. The memo text may want a
short note (or an update) reconciling the prose with this being the default
`mode="threshold"` policy, not the legacy trade.

Data quirks found while building this figure (worth a caption/text mention):
* `core`, `spiral`, `mid`, `core-inner`, and `long` meet the strict skirt
  <= 0.10 criterion at **every** tabulated resolution on their curve --
  entirely solid lines, no relaxation needed anywhere in their offered
  range.
* `mid+long`, `spiral+mid+long`, `main+long`, `mid+spiral+core-outer`, and
  `long+mid+spiral+core-outer` are relaxed at **every single point** on
  their imaging curve -- none of these `long`-containing composites ever
  reaches skirt <= 0.10 anywhere in their offered resolution range. Most of
  that relaxation stays within the 0.25 trade cap ("traded", dashed), but
  each of these five has a handful of points (9-21, concentrated at the
  finest resolutions near `long`'s own native beam) whose best achievable
  skirt exceeds 0.25 ("relaxed", dotted) -- visible as short dotted
  stretches for `main+long` and `long+mid+spiral+core-outer` in the plot.
* `core+spiral`, `spiral+mid`, and `main` are relaxed over a substantial
  fraction of their curves (42/181, 136/210, 216/245 points respectively)
  but never beyond the 0.25 trade cap -- dashed only, no dotted, for these
  three.
* `spiral+core-outer` is relaxed (dashed only) over 36/81 points.

## figs/heatmap.pdf

Robust-taper lattice heatmap for **`main`** (chosen because its lattice is
very well filled: 255/259 raw sweep rows `ok`, 4 `capped`, essentially no
gaps -- `core`'s lattice is comparably full, 336/337 `ok`, but `main` was
preferred per the brief's "main if well filled" rule and it best exercises
the heterogeneous beam-cap and relaxed-imaging behavior).

Data source: the raw sweep-result table `curvegen/results/main.csv` (one row
per measured (weighting, robust, taper) lattice cell: `res_geo_arcsec`,
`sigma_dirty`, `skirt`, `status`), assembled into the canonical rectangular
cell grid by `mr.build_heatmap()` (which internally calls
`curvegen.config.grid_rows()` for the taper axis and marks cells `env=True`
when they anchor a point on the default s0=0.10 imaging curve). This is the
exact same function + data path the HTML report's per-subarray heatmap
uses.

Plot details:
* Color = eta (`sigma_dirty / sigma_nat`), clamped to [1, 5] with a
  sequential colormap (`cividis_r`), matching the report's own eta-ramp
  convention (1 -> pale, 5 -> dark).
* x-axis (uv taper FWHM at 30 GHz, **mas** -- `main` native resolutions are
  sub-mas to sub-arcsec, so mas avoids awkward leading zeros) is genuinely
  log-scaled for the 18 nonzero tapers; the untapered (taper = 0) column is
  a sentinel one log-step to the left of the finest nonzero taper, with an
  explicit "0" tick label, per the brief.
* y-axis (Briggs robust, -2.0 to +2.0 in the canonical 0.4 steps) similarly
  sentinels the natural-weighting row 0.4 above robust = +2.0 with a
  "natural" tick label.
* Black solid/dashed contours mark skirt = 0.10 and skirt = 0.25. With only
  10 rows x 19 columns the contours are visibly blocky/jagged (a genuine
  coarse-lattice artifact, not a smoothing bug) -- worth a one-line caption
  caveat.
* Red open circles mark cells that anchor the default (s0 = 0.10) imaging
  curve (`env=True` from `build_heatmap`).
* No cells needed the "not measured" marker for `main` -- the lattice is
  essentially complete (see above), so that code path is present but did
  not draw anything for this subarray; it would trigger for a sparser
  lattice (e.g. `core+mid`, not offered).

## Caveats for the memo generally (not specific to one figure)

* The stale "eta-skirt trade is the primary imaging objective" prose in
  Sec. "Curve engine: query time" versus the shipped `mode="threshold"`
  default is the most substantive finding from building these figures --
  worth reconciling in the text (see the imaging.pdf section above for the
  detail).
* All curves reflect the `eta <= 5` display trim inherited from
  `make_report.main()`; the underlying engine does not itself censor by
  eta (see `envelope.py` `ETA_CAP` comments), so the *tool* can return
  answers beyond what these figures show.
