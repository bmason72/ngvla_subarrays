# Documentation audit — 2026-09-07

Read-only review of the docs listed in the audit brief, checked against the
6-7 Sep decisions in `docs/worklog/mfs-campaigns.md` and against the actual
scripts/flags on disk. No files other than this one were touched.

Summary: the single most important gap is that the "working-tree freeze"
hazard (a running Slurm campaign imports `curvegen/`/`sa_select/` from this
checkout at each stage start, so code/registry edits on `main` mid-campaign
are unsafe) is stated in only one place — buried in a dated worklog log
entry — and not in CLAUDE.md, RUN_CAMPAIGNS.md, or NEXT_AGENT.md, where an
agent is most likely to look before editing. Second, `docs/plans/NEXT_AGENT.md`
and `docs/ops/RUN_CAMPAIGNS.md` both still say the MFS snapshot production
run is "ready to launch" / "READY TO LAUNCH", but the same worklog records
it as already launched (job 3475087, 7 Sep ~12:15 CDT) — a same-day
contradiction an agent could act on wrongly. Third, `docs/plans/RELEASE_PLAN.md`
and `docs/plans/MFS_CAMPAIGN_PLAN.md` carry Aug-vintage status blocks
("Launch pending bmason", "point-source curves only initially") that
directly contradict later, better-sourced decisions (D5: both curves) and
should carry forward-pointers. All commands checked against the filesystem
resolved to real scripts/flags; no broken commands were found. Terms "map",
"combo", and "anchor" are used repeatedly without a single definition
anywhere in the read set.

1. `docs/plans/NEXT_AGENT.md:9` and `docs/ops/RUN_CAMPAIGNS.md:3` —
   quoted: "START HERE (7 Sep 2026) — MFS snapshot production run ready to
   launch" / "READY TO LAUNCH". Problem: `docs/worklog/mfs-campaigns.md:216-223`
   (same date) records the campaign as already launched by bmason at
   ~12:15 CDT 7 Sep (prep 3475087 running, sweep 3475088_[0] and collect
   3475089 pending). An agent reading NEXT_AGENT or RUN_CAMPAIGNS first
   (both are in the prescribed read order) would relaunch a running
   campaign. Fix: change both headings/lead sentences to "LAUNCHED 7 Sep
   2026 ~12:15 CDT (job 3475087); see docs/worklog/mfs-campaigns.md for
   live status" and move the launch command under a "for reference" note.

## Suggested single glossary

One-line definitions, drawn from the clearest existing statement of each
term (source noted); none of these currently exist together in one place.

- **eta (η):** image rms at a given resolution divided by the natural-
  weighting rms (natural = 1.0). (CLAUDE.md:49-51)
- **point-source curve:** the min-eta path to each resolution, ignoring
  PSF skirt. (docs/architecture/selection-tool-design.md:62)
- **imaging curve (sculpted curve):** the min-eta path to each
  resolution subject to PSF skirt <= threshold. (selection-tool-design.md:63)
- **skirt (shoulder):** the PSF value at radius = 1 clean-beam FWHM from
  the peak, azimuthally averaged; sculpting default threshold 10%.
  (CLAUDE.md:57-59; docs/plans/PLAN.md:56-57)
- **taperability:** the property/curve of how eta trades against
  resolution as UV taper and Briggs robust are varied. (CLAUDE.md:49-54)
- **LAS (largest angular scale):** the largest scale structure a
  subarray can image, ~0.6 lambda/b_min (SBA) to ~0.85 lambda/b_min
  (core), scaling with wavelength. (CLAUDE.md:55-56)
- **map (adaptive-sampler sense):** one subarray's, one campaign combo's
  (robust, taper) -> (eta, beam, skirt) surface, as certified or filled
  by the adaptive sampler. (inferred; not defined in the read set — see
  finding 7)
- **sample / curve / envelope:** a sample is one measured
  (robust, taper) -> (eta, beam, skirt) grid point; a curve is the
  derived eta(resolution) function built from samples; the envelope is
  the min-eta curve across all samples for a subarray/curve-type — what
  gets rendered and queried. (usage consistent across sa_select/README.md
  and RUN_CAMPAIGNS.md, but no single defining sentence found)
- **combo:** a `(rev, sim_mode, band)` registry key identifying one
  campaign's data/report/config namespace; an empty band is a legacy
  mono (30 GHz single-channel) campaign. (README.md:31; see finding 8 for
  the older two-axis usage in the PSF-backfill table)
- **band4 (internal key) / "MFS snapshot" (user-facing name):** the
  registry's internal tag for the Ka-band multi-frequency-synthesis
  broadband campaign; never shown to the user, who instead sees "MFS
  snapshot" (or "Rev F - MFS snapshot"). (D7, docs/worklog/mfs-campaigns.md:111-115)
- **fixed field of view (memo-121 convention):** image size held fixed
  in pixels; cell size grows with taper beyond the native beam, so this
  convention is exact at the fine end and for natural weighting, and
  only approximate at coarse-taper Briggs points (effect on eta not yet
  quantified). (D9, docs/worklog/mfs-campaigns.md:120-126; CLAUDE.md:151-153)
- **anchor:** a curve point that is actually rendered/displayed on a
  campaign's report envelope (as opposed to any measured lattice sample);
  PSF backfill targets anchors specifically because those are what the
  report shows. (inferred from docs/ops/RUN_CAMPAIGNS.md and
  docs/architecture/PSF_DIAGNOSTICS.md usage; no single defining sentence
  found)
- **canonical taper(s) / lattice:** the fixed 14-level logarithmic taper
  grid (plus taper 0) used as the standard sampling axis across mono and
  MFS campaigns. (count given only in passing, docs/worklog/mfs-campaigns.md:12)
- **snapshot vs. track (sim_mode):** track = 4 h synthesis; snapshot = a
  single ~60 s correlator dump. (docs/plans/MFS_CAMPAIGN_PLAN.md:57, "60 s
  dumps as now" — the clearest statement found, though not in a
  definitions-style location)
